01 / Why a program

An account is already a program.
It just isn’t written as one.

Policies decide which forms a placement needs. Automations wait, branch, and email. Access rules filter what a group sees. Writing those decisions as one checked program brings the tools software already relies on.

01

One reviewable file

Attributes through integrations live together, so a change is a diff a teammate can read. Northwind fits in 153 lines.

02 / Quick start

Write, check,
lower, and play.

  1. WriteA .lisp account program
  2. ReadForma reader, with source locations
  3. CheckNames, types, vocabularies, and fact scopes
  4. LowerJSON-safe resources, one or more per declaration
  5. PlayThree-state policies, scenarios, and coverage

Clone the repository and run the checker on the Northwind account. It exits non-zero on any error, on a failing scenario, or on a policy or automation decision that no scenario sees both true and false.

pnpm install --frozen-lockfile
pnpm account:check examples/onboarded/northwind.account.lisp
pnpm account:check examples/onboarded/northwind.account.lisp --json

The elaborator lives in examples/onboarded/account: elaborate.ts reads and checks, lower.ts emits resources, and evaluate.ts runs policies and scenarios.

03 / Language guide

Nine verbs.
One account.

Each top-level declaration names something the rest of the file can use. Paths such as placement.union-local name attributes, keywords such as :warehouse name choices, and source names are kebab-case; lowering maps them to the platform’s snake_case. Every example below is quoted from northwind.account.lisp. Open Lowers to to see the recorded resources.

account

Who this is, and the namespace for every key.

(account name "Title" :languages [:en ...] :sender "email" :support "email" :dedupe [paths])

A program starts with exactly one account. Its name prefixes every key, so union-card becomes northwind.union-card. The first language is the default; the others enable per-field translations. :dedupe lists the attributes that identify a duplicate employee.

Checked

  • Exactly one account, declared first
  • Deduplication paths name known placement facts
(account northwind "Northwind Logistics"
  :languages [:en :es]
  :sender "onboarding@northwind.example"
  :support "people@northwind.example"
  :dedupe [employee.email])
Lowers to

attributes

Typed custom attributes on built-in entities.

(attributes entity (name type "Label" :searchable :sensitive :scope :pattern "re" :deprecated "why") ...)

Extend employee, employer, client, job, or placement. Types are string boolean date datetime integer decimal address, or a closed choice: (one-of :value "Label" ...). :scope marks an attribute that access rules may read. A deprecated attribute stays readable but cannot be written.

Checked

  • Names are unique, kebab-case, and not built-in
  • :sensitive excludes :searchable and :scope; addresses take no flags
  • :pattern applies to strings and must be a valid expression
  • Choice options are unique keywords with non-empty labels
(attributes employee
  (badge-number string "Badge number" :searchable :pattern "^NW-[0-9]{6}$")
  (union-card-number string "Union card number" :sensitive)
  (mailing-address address "Mailing address")
  (forklift-certified-on date "Forklift certification date")
  (legacy-hris-id string "Legacy HRIS ID" :deprecated "Replaced by badge-number"))
Lowers to

rule · def

Name a decision once and reuse it everywhere.

(rule name expression)    (def name arithmetic)

Rules combine = not= > >= < <=, in, missing?, and, or, and not over attribute paths. They evaluate to true, false, or unknown: a fact that is not recorded is unknown, and and is false as soon as any part is false. A rule is inlined wherever it is used, and the reader’s fact scope is checked at that use. def evaluates arithmetic at build time.

Checked

  • Choice values exist, with a suggestion for near misses
  • Comparisons match the attribute’s type; ordering needs a number or date
  • Rules are defined before use
(rule union-covered
  (and (not= placement.union-local :none)
       (>= placement.weekly-hours 20)))

(def dues-rate (/ 1.5 100))   ; build-time arithmetic, inlined as 0.015
Lowers to

form

Pages and fields; reads and writes are inferred.

(form name "Title" :due-in days (page "Title" :employee field ...) ...)
(form name :from "package" :key "key")

A field binds an attribute path, which the form writes, or a bare name, which becomes a form answer. Fields are checkbox text number date address dropdown signature formula review content, with :required, :show-if rule, and translations such as :es "…". :due-in sets the task due date. A :from form references one another package owns.

Checked

  • The field suits the attribute: a checkbox writes a boolean, a date writes a date
  • No writes to deprecated or built-in attributes, and each attribute is written once
  • Answers are unique, and :show-if reads only earlier answers
  • Local keys stay in the account namespace; :from keys stay outside it
(form union-card "Union card"
  :due-in 30
  (page "Union membership" :employee
    (checkbox has-card "I already hold a union card" :es "Ya tengo una tarjeta sindical")
    (text employee.union-card-number "Union card number" :required :show-if has-card)
    (address employee.mailing-address "Mailing address" :required)
    (formula weekly-dues "Estimated weekly dues"
      (round (* job.hourly-rate placement.weekly-hours dues-rate) 2))
    (signature employee-signature))
  (page "Steward review" :employer
    (review [employee.union-card-number weekly-dues])
    (signature steward-signature)))
Lowers to

policy

When a placement matches, require forms.

(policy name "Title" :when rule :require [form (form :when rule) ...])

A policy applies when its :when rule is true, then requires each listed form, optionally behind its own rule. When a rule is unknown, the policy or form is undecided rather than skipped, and the evaluator reports the missing facts.

Checked

  • Rules read only placement, employee, employer, client, and job facts
  • Each form appears at most once per policy
  • Every form reference resolves
(policy warehouse-onboarding "Warehouse onboarding"
  :when at-warehouse
  :require [w4 site-safety
            (drug-screen-consent :when client.requires-drug-screen)])
Lowers to

automation · param

A trigger, then steps.

(automation name "Title" :on (task-created form) step ...)
step: (wait n :days :after path) (when rule step ...) (email :employee template "Subject" "Body") (assign form)

Triggers are (task-created form), (task-completed form), and (placement-created). Steps run in order; when runs its steps only when the rule is true. Email bodies render {{ entity.field }} variables. A param is a value each target account supplies, such as an email template.

Checked

  • Task triggers may read task and employee facts; placement triggers read placement facts
  • Waiting after task.due-at requires the form’s :due-in
  • Templates are :sendgrid-template parameters; variables exist and are in scope
  • Rendering a sensitive attribute is a warning
(param overdue-template :sendgrid-template "Supplied per target account.")

(automation union-card-reminder "Union card reminder"
  :on (task-created union-card)
  (wait 2 :days :after task.due-at)
  (when (not= task.status :completed)
    (email :employee overdue-template "Your union card is overdue"
      "Hi {{ employee.first_name }}, please complete your union card.")))
Lowers to

group

Permissions, plus what the group can see.

(group name "Title" :can [:entity/verb ...] :sees rule)

:can grants permissions such as :task/edit. :sees is an access rule over the records the group may view, and it may read only attributes declared with :scope. That boundary is checked through named rules as well.

Checked

  • Permissions come from a known set, with suggestions
  • Access rules read only :scope attributes
(group west-managers "West region managers"
  :can [:placement/read :employee/read :task/read :task/edit]
  :sees (= client.region :west))
Lowers to

integration

Pin a provider; leave credentials with the account.

(integration name "provider@revision" :connection "reference" :setting value ...)

An integration names an exact provider revision, a connection reference the target account resolves, and only the settings it uses. The program never holds a credential.

Checked

  • The provider revision is pinned
  • A :connection reference is present
(integration checkr "@onboarded-platform/checkr@1.4.0"
  :connection "checkr"
  :package "driver_pro"
  :adjudication :manual)
Lowers to

scenario

Facts in, outcomes out, on any day.

(scenario "Title" {path value ...} (expect ...) (day n (record path value) (complete form) (expect ...)))
expect: :policies [..] :forms [..] :unknown {name [paths]} :tasks [..] :open [..] :emails [..]

A scenario creates a placement from its facts on day 0. Policies assign tasks, and automations run. day moves the clock forward, resuming any waits, then records facts, completes tasks, and checks expectations. When an expectation names policies or forms, undecided outcomes must be listed under :unknown.

Checked

  • Facts are typed; task facts come from the simulation
  • Days increase; completed forms write only what they declare
  • Every policy and automation decision is seen true and false across scenarios
(scenario "union local recorded on day five"
  {job.site-type :office placement.weekly-hours 32}
  (expect :forms [] :unknown {union-card-obligation [placement.union-local]})
  (day 5 (record placement.union-local :local-42)
         (expect :policies [union-card-obligation] :tasks [union-card])))

    08 / Status

    What runs today,
    and what would come next.

    The account program is example code, separate from the package’s portable ontology IR. It shows the shape of an Onboarded prelude; it is not one yet.

    Runs in this repository
    • Forma reader parsing, with every check reported at a line and column
    • Type, vocabulary, fact-scope, permission-scope, and reference checks
    • Lowering to directional account, property, form, policy, automation, group, and integration resources
    • Three-state policy evaluation and a day-by-day scenario simulator with decision coverage
    Not built
    • Production resource formats or byte-identical snapshots of them
    • Planning against, or deploying to, a live Onboarded account
    • Form rendering, Liquid beyond simple variables, and runtime formula evaluation
    • Integration behavior, persistence, authorization, or an onboarded Forma prelude
    The direction

    Write the account once, prove it with scenarios, and let a prelude elaborate the same declarations to the platform’s own configuration.
