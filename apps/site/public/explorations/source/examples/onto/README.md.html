1# An OntoLang-style language, running on Triplex
2 
3[OntoLang](https://onto.space/ontolang) describes actors, typed business records,
4formulas, rules and stories. This independent example loads an OntoLang-shaped
5language as a Forma prelude, lowers its language IR to Open Ontology's portable
6`OntologyIR`, and runs the hotel story on the local in-memory Triplex runtime.
7It is experimental, with no Onto runtime integration, persistence or authorization.
8 
9## Read and run
10 
111. Read the language: [onto.lisp](onto.lisp).
122. Read the business model: [hotel.forma](hotel.forma).
133. Run the operations: `pnpm example:onto` from the repository root.
144. Compare the complete [checked output](output.json) and [lowered IR](../../test/fixtures/onto-hotel.ir.json).
15 
16Use Node 24 and pnpm 10.11.0; install with `pnpm install --frozen-lockfile`.
17The example's checker is `elaborateHotel()` in [lower.ts](lower.ts), exercised by
18`pnpm exec vitest run test/onto-example.test.ts`. The generic `model:check`
19command accepts the package's ontology DSL, not this external language.
20 
21The website's example notebook presents this README, full source with line
22anchors, model, run command and tested output together. It is a static reading
23notebook; execute the command in a clone. The browser does not host Triplex.

25## Three layers
26 
27| Layer | Source | Responsibility |
28| --- | --- | --- |
29| Language | `onto.lisp` | Syntax, types, scopes, expression inference, diagnostics, language IR |
30| Business model | `hotel.forma` | Actors, hotel objects, rules, formulas, stories, seed data |
31| Operations | `lower.ts`, `guards.ts`, `scenario.ts` | Portable IR, seed transactions, observed facts, guarded commands, queries and journal |
32 
33The path is `bootstrapFromSources` → `elaborateSources` → `lowerOnto` →
34`toTriplexConfig` / `makeOntologyRuntime` → `triples.transact`. The prelude stays
35in this example; it is not a bundled package language. `lowerOnto` is pure;
36seed operations and host guard metadata are separate from the JSON-safe IR.
37 
38## OntoLang to Forma
39 
40| OntoLang | Forma (`onto.lisp`) |
41| --- | --- |
42| `actor Guest @type person` | `(actor Guest :person "doc" {fields})` (+ `:joins :sign-up`/`:invite`/`:none`) |
43| `object Reservation`, `status: a \| b @final` | `(object Reservation "doc" :final {:status [...]} {fields})`, `:status (Union :a :b)` |
44| `guest: Guest`, `services: Service[]` | `(One Guest)`, `(Many Service)` |
45| `string`/`int`/`timestamp` | `String`/`Int`/`Instant` |
46| `@rule …` | `(rule name Object "doc" expr)` |
47| `total: int = …` | `(formula Object field Type "doc" expr)` |
48| story sentence + `requires`/`sets` | `(step Actor verb Object :to Actor :requires [...] :sets {...})` inside `(story …)` |
49| `seed RoomClass` | `(seed RoomClass [{...}])` |
50 
51## What executes
52 
53All 17 declarations elaborate without diagnostics. Actors and objects become
54nine object types. Links become `ref` properties, `Many` preserves cardinality,
55and unions become string properties. Attribute keys are explicit, for example
56`:room-class/rate` and `:reservation/check-in`. The five story steps become
57five actions. The runtime requires kebab-case action names, so the check-in
58name is `hotel-booking-checks-in`. Updating a status clears then sets it.
59`:new true` produces `create-object`; the host also rejects an existing id.
60 
61The run seeds three room classes, supplies a guest, room and invoice fixture,
62then submits, confirms, rejects an early check-in, accepts check-in at exactly
6315:00 UTC on November 4, 2026, requests a service and fulfils it. Reusing the
64request sentence on that fulfilled service is rejected because it is final.
65Reservation `declined` and `checked-out` are also terminal (tested).
66 
67`Reservation.service-charges` becomes a named Datalog sum query over explicitly
68linked, fulfilled services. It returns 75 after fulfilment. Like a grouped SQL
69sum, the sparse query returns no row when no fulfilled service matches; a
70missing reservation group represents zero. It does not store a derived field.
71The date-order rule also becomes the named `check-out-after-check-in` query,
72which returns reservations satisfying the comparison; it does not reject writes.
73The run prints both named queries, room classes, story outcomes, and journal
74actor and command ids. Rejected commands have no journal entry.
75 
76Creation inputs supply all single-valued fields that the sentence does not
77set, including reference ids. Collection membership is explicit facts. The
78fixture separately asserts `Reservation.services`: the language does not
79specify automatic inverse maintenance from `Service.reservation`.

81## Guards and atomicity
82 
83[guards.ts](guards.ts) interprets `requires` against entity views read from
84Triplex: `is?`, `known?`, `in?`, `before?`, `after?`, `days-between`, `sum`,
85`now`, Boolean operators, arithmetic, and the `map`/`filter` lambdas used by
86the service formula. `known?` on a link requires the target to have live facts.
87Dates are UTC epoch milliseconds; `days-between` counts complete 24-hour days.
88The scenario passes fixed command times. The journal's commit clock belongs
89to the Triplex host, and is separate from that business clock.
90 
91**The example's guard and write are atomic with respect to observed entity
92facts.** Triplex 0.2.0 exposes `TransactionMeta.preconditions` with `EntityState`
93(the complete observed live triple-id set) and `TripleLive` (compare and
94retract). `makeOntologyRuntime.invoke` does not forward preconditions. The
95example decorates the scoped `Triples` service so its actual `transact` adds
96`EntityState` preconditions for every entity read, including linked records
97and the absence of a creation target. Triplex compares these inside its write
98transaction; conflicts reject the whole write. No `src/` changes are needed.
99Tests inject a competing write after evaluation to prove all three cases.
100 
101This is a bounded interpreter over three levels of links and ordinary,
102non-scheduled facts, not a general query guard system. Time is a command input;
103wall-clock passage is not a protected database fact. Direct runtime invocations
104or raw transactions bypass these example guards. There is no backend enum,
105transition or invariant enforcement. Follow-up work belongs in Triplex:
106command configuration nodes with guards and transition constraints, applied to
107all command entry points. `ActionTypeIR` would also need a portable guard contract.
108 
109## Not lowered
110 
111`notLowered()` reports these limitations and the run prints them:
112 
113- Rule `check-out-after-check-in`: a named satisfaction query runs, but there is no invariant enforcement.
114- Rule `past-bookings-are-settled`: its Boolean expression is checked; no clock-driven invariant enforcement.
115- Formula `Invoice.total`: checked, but its date arithmetic and derived-field composition have no faithful lowering here. The interpreter's vocabulary is tested; the run does not compute invoice totals.
116- `requires` and final states: example host guards, absent from `ActionTypeIR`.
117- Actor type, joins and counterpart: descriptive data; no identity or authorization enforcement.
118- Union members: prelude checks, stored as strings without runtime enum constraints.
119- Many references: schema retained, collection membership transacted explicitly.
120 
121Only the exact service-charge and date-order expressions are recognized for query
122lowering. Changing either causes it to be reported rather than silently reusing
123the old query.
124Other unsupported field types throw an error. The rule query is an observation; the business rules do not become write-time
125Datalog constraints or scheduled background jobs.
126 
127## Diagnostics
128 
129The test creates each broken variant with a string replacement and asserts the
130code, severity and message. Expression inference follows linked record views,
131including `invoice.reservation.room-class.rate`.
132 
133| Broken variant in `hotel.forma` | Diagnostic |
134| --- | --- |
135| `reservation.check-in` → `reservation.checkin` in a rule | `elaborate/hole-type`: missing record field |
136| `invoice.reservation.room-class.rate` → `.name` | `elaborate/hole-type`: type mismatch |
137| `:sets {:status :checked-in}` → `:checked_in` | `onto/unknown-state` |
138| `(is? reservation.status :confirmed)` → `:confirmd` | `onto/unknown-state`, lists valid states |
139| Remove `:new true` from Guest submits Reservation | Warning `onto/unguarded-transition` |
140| `:room (One Room)` → `(One Suite)` | `onto/unknown-link` and `elaborate/hole-type`: unknown type Suite |
141| `(formula Invoice total Int` → `String` | `elaborate/hole-type`: expected String, found Int |
142| `(step Concierge fulfils Service` → `Booking` | `elaborate/hole-type`: unknown reference Booking |
143| Seed `:rate 200` → `:price 200` | `onto/unknown-field` |
144 
145Removing `:new true` exposes a real ambiguity: a submission sentence with no
146current-state guard could otherwise revive a declined reservation.
147 
148The supplied monomorphic `is?` workaround stays in the prelude. Forma's
149keyword inference and missing-hole destructuring issues were addressed upstream
150in [Forma PR 110](https://github.com/bjacobso/forma/pull/110); this example does
151not implement either compiler fix.

153## Forma package provenance
154 
155The npm 0.3.0 tarball predates the descriptor API used here. This example uses
156an isolated, MIT-licensed snapshot of latest Forma `main` (resolved to commit
157`535cd41ec7f81f3229b810df6f374ebfa04c16c7`) as the development package
158`@open-ontology/onto-forma`; the package's existing `@formalang/ts` dependency
159stays unchanged. See [the provenance and rebuild instructions](../../vendor/README.md).
160Both APIs are consumed through package exports; no sibling project source is imported.
