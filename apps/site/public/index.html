Turn how a business works into a model that runs.

Open Ontology is a small, closed language for domain models. It covers the things a business tracks, how they connect, what people do to them, and the questions they ask. Agents write the model, a checker verifies it, and people own the result: one plain file that compiles to portable JSON and runs.

01The language

Four declarations. Four changes. That is the whole language.

A closed vocabulary is easier to write correctly and easier for the person to review. It also leaves no room to invent structure the business does not have. If they know Palantir Foundry's Ontology, it is the same core (objects, links, actions) as an open file they own.

Nouns

define-entity

A thing the business tracks, with namespaced fields. A field typed as another entity is a reference.

(define-entity Ticket
  (:field [ticket/title String {:required true}])
  (:field [ticket/customer Customer {:required true}])
  (:field [ticket/priority Int {:required true}]))
Connections

define-relation

A typed edge between two entities that carries its own facts, such as when or why.

(define-relation escalated-to Ticket Engineer
  (:field [escalated-to/reason String {:required true}])
  (:field [escalated-to/at Instant {:required true}]))
Verbs

define-action

Something a person does. Its typed inputs are decoded first, and its changes commit as one transaction.

(define-action close-ticket
  (:input [ticket String {:required true}])
  (:returns String)
  (:do (changes
    (clear ticket :ticket/status)
    (set ticket :ticket/status "closed"))))
Questions

define-datalog-query

A named question over the same facts, with joins, negation, ordering and aggregates.

(define-datalog-query tickets-by-status
  (:query
    {:find ["?status" "?count"]
     :where [["?t" ":ticket/status" "?status"]]
     :aggregate [["count" "?t" "?count"]]}))
ChangeSyntaxEffect
create(create Entity id {:ns/field value})Asserts each listed field on object id.
set(set object :ns/field value)Adds a value. It does not remove the old one.
clear(clear object :ns/field)Retracts every value. Put it before set to replace.
link(link relation from to {:rel/field value})Creates the link object between from and to.

A value is an input name, now, or a quoted literal. Nothing else: no conditions, no computed values. Full grammar, types and naming rules are in the agent guide, section 5.

02The procedure

From a conversation to a checked model.

The same seven steps work for any domain. The agent does the translating, and the person only has to confirm what they recognize.

  1. Draft before interrogating. Write a first model from whatever the person gave you. Ask only about the gaps.
  2. Fill gaps by area: things, facts, connections, verbs, questions.
  3. Map words to forms using the table alongside.
  4. Name things by the rules: PascalCase entities, kebab-case everything else, namespace/field keys.
  5. Check: run pnpm model:check model.lisp until it reports 0 warnings.
  6. Run a scenario: seed facts, invoke actions, compare the query rows with what the person expects.
  7. Hand back the file, the check summary, the scenario output, and what v0.1 cannot express yet.

03Check

Errors with line numbers. Warnings for what compiles but misbehaves.

pnpm model:check elaborates a .lisp or .ts model and applies the runtime's naming and input rules. It also lints for the mistakes that fail silently: a misspelled attribute, a value that is never replaced, an input that can't be omitted. Add --json for machine-readable output.

04Run

What happens when an action runs.

The field-service example seeds three facts, invokes assign-work-order on behalf of a dispatcher, and asks assigned-work. Each step below is the real behavior of the v0.1 runtime on the in-memory Triplex host.

  1. 1

    Facts exist

    The scenario seeds what is true before anyone acts.

    entityattributevalue
    technician:ada:technician/name"Ada"
    work-order:42:work-order/title"Repair cooling pump"
    work-order:42:work-order/status"open"
  2. 2

    Someone acts

    The input is decoded against the action's schema before anything is written. actor is recorded on every fact, and reusing a commandId fails with CommandAlreadyCommittedError.

    runtime.invoke("assign-work-order",
  { workOrder: "work-order:42", technician: "technician:ada" },
  { actor: "dispatcher:grace", commandId: "assign:42", now: 1_800_000_000_000 })
  3. 3

    One transaction commits

    The three changes become five operations, and they commit together or not at all.

    opentityattributevalue
    retractwork-order:42:work-order/status*
    assertwork-order:42:work-order/status"assigned"
    assertlink:assigned-to:work-order:42:technician:ada:assigned-to/fromref work-order:42
    assertlink:assigned-to:work-order:42:technician:ada:assigned-to/toref technician:ada
    assertlink:assigned-to:work-order:42:technician:ada:assigned-to/assigned-at1800000000000
  4. 4

    The question is answered

    runtime.query("assigned-work") joins the work order, the link and the technician. It returns rows keyed by variable:

    [{ "?title": "Repair cooling pump", "?technician": "Ada" }]

05Portable

Two syntaxes. One JSON contract.

The IR is the contract, and either syntax is enough to write a model. Forma, used on this page, is compact, and its errors point at a line and column. It is optional. The TypeScript DSL type-checks queries against declared properties. Both compile to the same IR, and the test suite asserts that the two field-service models produce identical JSON. Store it, diff it, or hand it to another tool.

model.lispForma
(define-entity WorkOrder
  (:field [work-order/title String {:required true}])
  (:field [work-order/status String {:required true}]))
model.tsTypeScript
const WorkOrder = Ontology.ObjectType("WorkOrder", {
  properties: {
    title: Property.make(":work-order/title", Schema.String).required(),
    status: Property.make(":work-order/status", Schema.String).required(),
  },
});

06Limits

What v0.1 does not do. Say so before you promise it.

The model is the part that carries forward. The runtime today is a local check, and the list on the right is what the next checkpoint adds.

Works today

  • Authoring in Forma or TypeScript, compiled to one JSON IR
  • Located errors, naming rules and lint with pnpm model:check
  • Actions as atomic, attributed, idempotent Triplex transactions
  • Named Datalog queries: joins, not, comparisons, aggregates, ordering, limit and offset
  • Two runnable examples: field service and support desk

Not yet

  • Persistence: in-memory host only, so nothing survives the process
  • Authorization: actor is recorded, not checked
  • HTTP, OpenAPI or UI surfaces, and an npm release
  • Query parameters, deletes, unlinks, conditional actions
  • Write-time enforcement of required and cardinality

Next checkpoint

  1. SQLite persistence
  2. Policy authorization
  3. Versioned config release and deploy
  4. Restart and historical-query tests
  5. Attribution and idempotency verification
  6. Migration or rebuild procedure

Then HTTP reflection and OpenAPI.
