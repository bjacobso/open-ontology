01The missing model

The business is connected.
The configuration is scattered.

Consider a billing plan copied into a CRM picklist. A change to pricing also means a change to sales. The idea is to record that dependency in source, so the two models can be reviewed together.

Billing · Stripepro_monthlybilling/pricing.formaThe price book defines the plan.
←refers toproposed typed reference
CRM · SalesforceOpportunity.Plan__csales/opportunity.formaThe picklist uses that definition.

An ontology names the things and the relationships between them. The proposal is to carry those relationships across platform DSLs, rather than copying the same business definition into each system.

02Three DSLs to imagine

Different vocabularies.
One business to describe.

A Forma prelude supplies domain-specific forms. These design studies explore what Salesforce, Stripe, and Foldkit preludes could look like. They are not installable packages, checked examples, or generated output.

ACRM metadata

Salesforce, as a DSL.

The objects and rules your sales team works with, in a file you can review.

Proposed · not implemented

The pricing launch

Billing introduces a new plan. Sales needs the same plan in its CRM. What if the picklist could refer to the price book?

The proposed language would describe objects, fields, and validation rules. A generator would produce Salesforce metadata, while keeping the source model readable. Cross-platform references would need a shared type contract.

Target vocabulary: Salesforce CustomField metadata ↗

sales/opportunity.formadesign study
(import "@acme/billing" :as billing)

(object Opportunity
  (field Plan__c
    (picklist-of billing/prices :by :lookup-key))
  (field Seats__c (Number :precision 6)))

(validation-rule seats-required Opportunity
  (and (= StageName "Closed Won")
       (blank? Seats__c))
  "Closed deals need a seat count.")

Desired output: reviewable metadata files. No Salesforce elaborator or API integration ships in v0.1.

BBilling configuration

Stripe, as a DSL.

A price book you can read as a price book.

Proposed · not implemented

The shared definition

The monthly plan has a name, a currency, and a billing interval. Describe it once, then let other models refer to it.

The proposed language would describe products and prices, and export a price book for other DSLs to use. A generator would translate the model into Stripe API parameters. Applying changes would require a separate reconciliation design.

Target vocabulary: Stripe products and prices ↗

billing/pricing.formadesign study
(product pro "Pro")

(price pro-monthly pro
  :lookup-key "pro_monthly"
  :currency :usd :unit-amount 2900
  :recurring :month)

(price pro-annual pro
  :lookup-key "pro_annual"
  :currency :usd :unit-amount 29000
  :recurring :year)

(export prices [pro-monthly pro-annual])

Desired output: explicit API parameters. No Stripe generator, credentials handling, or deploy command ships in v0.1.

CApplication models

Foldkit, as a DSL.

Give the domain an application model you can follow.

Proposed · not implemented

The application layer

A billing screen offers the same plans as the CRM. What if its model referred to the price book too?

Foldkit is a TypeScript frontend framework built on Effect, with explicit Models, Messages, update functions, and Commands. A proposed Forma DSL could describe app models and messages, then generate TypeScript for a Foldkit application.

Framework and architecture: foldkit.dev ↗

app/billing.formadesign study
; Illustrative Forma syntax, not a Foldkit API.
(import "@acme/billing" :as billing)

(model Billing
  {:selected-plan (Option String)
   :is-saving Bool})

(message SelectedPlan {:key String})
(message SubmittedPlan {})
(message CompletedSave {})

; How should billing/prices type the selection?
; Updates and Commands need their own design.

Desired output: Foldkit TypeScript model and message declarations. This repo has no Foldkit dependency, prelude, generator, or workbench.

03A shared vocabulary

Connect the concepts.
Keep the differences.

A CRM account and a billing customer could both refer to an organization in your domain. That would not make their fields, identities, or lifecycles interchangeable. A shared vocabulary needs explicit mappings.

Proposed correspondences · no shared business-type library ships yet
Domain conceptCRM modelBilling modelQuestion to make explicit
OrganizationAccountCustomerWhich records describe the same business?
PlanOpportunity plan fieldPrice lookup keyWhich definition owns the allowed values?
MoneyDeal amountPrice amount + currencyHow do units and currencies map?

A small piece of this approach works today: the bundled Git vocabulary and GitHub hosting model share repository, branch, and commit types. They model a local graph; they do not configure GitHub.

04The working foundation · v0.1

A real ontology DSL.
A small, tested runtime.

Forma and TypeScript compile to the same JSON-safe IR. The Triplex adapter runs actions and named Datalog queries on a local in-memory host. This field-service example is checked in and exercised by the conformance tests.

Implemented · experimental

Name the things.
Define the links.

The working language uses define-entity, define-relation, define-action, and define-datalog-query. The checker reports source locations and warns about common modeling mistakes.

In this example, an action assigns a work order to a technician. The query returns the order’s title and the technician’s name.

Read the complete model ↗
Read the equivalence and runtime tests ↗

examples/field-service/model.lispreal source · excerpt
(define-entity Technician
  (:field [technician/name String {:required true}]))

(define-entity WorkOrder
  (:field [work-order/title String {:required true}])
  (:field [work-order/status String {:required true}]))

(define-relation assigned-to WorkOrder Technician
  (:field [assigned-to/assigned-at Instant {:required true}]))

05The honest boundary

What runs. What’s proposed.
What needs an answer.

This is an experiment, not a platform rollout. Read the Salesforce, Stripe, and Foldkit proposals, or the architecture document for the package that exists.

Runs today · v0.1

  • Forma and TypeScript authoring with equivalent JSON IR
  • Model checking with located diagnostics and warnings
  • Actions and named Datalog queries on Triplex
  • Bundled /std/git and /github domain libraries
  • Local in-memory runtime; no durable server or authorization layer

Proposed · not implemented

  • Salesforce, Stripe, and Foldkit DSLs and generators
  • A shared business vocabulary with explicit platform mappings
  • Checking references across platform projects
  • A package registry and oo CLI
  • Planning and applying changes to live platforms

Open design questions

  1. Which platform and which small slice should come first?
  2. Who owns shared identities and mappings?
  3. How should models handle live configuration drift?
  4. Which changes need a human review before applying?

Proposed syntax is illustrative and may change. No provider package is available to install.

Useful today for experimenting with domain models, actions, and queries in a local host. A team looking to deploy Salesforce metadata or manage a Stripe account would need capabilities this package does not yet provide.
